### 2. Disabled the CLI harness's real-time throttling

While investigating a `simple4.ipl` run that appeared to hang after
printing its final result (`--timeout 15000` reported "likely
runaway/infinite loop"), re-running at a longer timeout showed it
actually halts cleanly after ~15.6-15.9s wall-clock -- and this ~15-16s
figure turned out to be a **fixed cost of loading the interpreter's own
~700+ card deck**, present even for the smallest `simple1.ipl`, not
specific to that program. Root cause: `envir.throttle()` paces execution
to real-1620 speed for no reason in a headless CLI run. Fixed by having
`tools/cli/run1620.mjs` override `processor.envir.throttle` to a no-op by
default (added `--real-time` to opt back into the original throttled
timing if ever needed for a genuinely timing-sensitive investigation).
Verified byte-identical output before/after across four `simple*.ipl`
files; wall-clock dropped from ~15.6s to ~3.6s. Documented in
`tools/cli/README.md`.

### 3. Major finding: the "J125 operates on the wrong field" mystery from the prior session was our own formatting bug

Jeff's hypothesis after seeing `simple4.ipl` show `J125` bump `70000` to
`70001` instead of `80000`: "I think we're putting in the numbers in the
wrong format." Checked `IPL-V-Interpreter-Mod-3-4.sps` and found `LINK
DS 5` -- LINK genuinely is a fixed 5-digit field. Built `simple6.ipl`,
identical to `simple4.ipl`/`simple5.ipl` except the `CONSTANT` cards'
value digit moved from the field's leftmost column (56) to its rightmost
(60). Result: **confirmed**. Punch output changed from `70000`/`70001`
to plain `7`/`8` -- exactly right. `J125` was never broken; every prior
`simple*.ipl` test (including the previous session's `simple8.ipl`,
"confirmed correct 3+4=7 in a x10000 encoding") had simply left-justified
its numeric constants in a 5-digit field, inflating every value by
10000x and inventing a fictitious "encoding" to explain it. Fixed and
re-ran `simple1.ipl`-`simple5.ipl` with right-justified constants; all
five now produce plain, correct values (see table in `log.md`'s
2026-09-11 22:16 PDT entry). This resolves the single biggest open
question flagged at the end of the prior session.

### 5. `simple3.ipl` correction: the trailing `0` isn't an operand

While investigating an edited `simple3.ipl` (two data terms, two
`PRINT RESULT, QUIT.` calls, the first missing its trailing `0`), Jeff
corrected an early wrong analysis: that trailing `0` on `J152` is not an
operand at all -- it's IPL's own **STOP/end-of-list marker** for the
routine. A bare `J152` (no `0`) just means the routine's instruction list
isn't finished yet; execution correctly falls through to the next card.
Both prints firing in that test was expected behavior, not a `J152`
quirk.

### 6. `F1.ipl` "flier": crash still reproduces, now localized to the exact IPL statement

Re-ran the still-open `F1.ipl` crash (`MAR Check: fetch() invalid memory
address=70603`, first seen in a prior session) with the improved harness.
Confirmed it's not the earlier harness race/throttling bugs -- same crash,
same address, now reproducible in ~3s instead of ~16s+.

- Used IPL-V's own monitor trace (Program Switches 1-4, output routed to
  the card punch per the prior session's finding) to map the crash back
  to source: `F1.ipl` completes its entire setup correctly -- creates an
  empty output list, locates the first input-list cell, finds symbol
  `B1` -- and crashes on source lines 33-34, the very first call to `J66`
  ("ADD THE SYMBOL TO THE OUTPUT LIST... IF IT IS NOT ALREADY ON IT"),
  trying to insert `B1` into what is still an empty output list. It never
  reaches `C1` or any other list element.
- Cross-checked against a full, un-throttled raw instruction trace (now
  cheap to generate, ~3s for the whole run instead of tens of seconds):
  `J66` maps to the interpreter's own `COLSYM` ("collect symbol")
  subroutine, and the crash happens right as it's about to call `RESBLK`
  ("reserve block" -- allocate a new list cell), during the instruction
  fetch immediately before ever entering `RESBLK`'s own code.
- Confirmed this is genuinely the **first-ever real allocation** in the
  run: grepped the full trace for both block-management routines --
  `FNDBLK` (find an existing free block, address `08002`) had already
  run 32 times harmlessly during interpreter bootstrap; `RESBLK` (address
  `08248`) had **zero** prior occurrences. The crash is specifically on
  the very first attempt to grow list-space storage, matching Paul's
  original suspicion (from the very first planning session) that this is
  a pushdown/list-space allocation bug, and matching the "TRAPPED ON H2"
  symptom seen with Ackermann(m, n>0).
- Not fixed this session -- localized, not resolved. Next step would be
  tracing exactly what's in memory around `NMBR`/`LADR` (the operands of
  the `TF` instruction that fails) right before the crash, to see what
  the interpreter expected to find there (probably a record mark it
  didn't get) versus what's actually present.

### 7. First working list-construction-and-print test

Pivoted to something simpler after the F1 detour: `simple8.ipl` builds a
4-element list (`L1 -> L2 -> L3 -> L4`) via plain data-header/list-cell
cards (no list-processing primitives involved in constructing it) and
prints it with `J151` (the same list-print primitive `F1.ipl` uses).

First attempt failed with `UNDEFINED REGIONAL SYMBOL` errors for the
list's continuation cells, even though the card columns were verified
byte-identical to `F1.ipl`'s own working template. Ruled out region size
(tried both 5 and 10) and region letter (`L0` vs `D0`) as the cause via
substitution tests. **Jeff's correction**: the list cells' content
symbols (`X1`/`Y1`/`Z1`, invented names) aren't free-form labels -- in
IPL-V a symbol *is* a region-letter-plus-digit reference, and I'd
referenced regions `X0`/`Y0`/`Z0` that were never declared. Fixed by
reusing the already-declared `L0` region for the content atoms
(`L2`/`L3`/`L4`), mirroring how `F1.ipl`'s own list content (`B1`/`C1`/
`A1`) references its pre-declared `B0`/`C0`/`A0` regions. Result: clean
load, no errors, `J151` correctly punches all four list elements
(`L1`, `L2`, `L3`, `L4`).

## Architecture Notes / Gotchas for next time

- **A data term's `LINK` field is a fixed 5-digit field (`LINK DS 5` in
  the interpreter source) and must be right-justified.** A single-digit
  constant belongs in the field's *last* column (60 in this card
  layout), not its first (56) -- left-justifying it (as every
  `simple*.ipl` test before this session did) inflates the value by
  10000x and looks exactly like a deliberate "value x10000 encoding" if
  you only check the punch output once. Always double check by changing
  the value and confirming the punch output changes by the same amount,
  not by a scaled amount.
- **A `J152`/`J151` card's trailing `0` is a STOP/end-of-list marker for
  the routine, not an operand.** Its absence means "this routine's
  instruction list continues on the next card," not "don't quit."
- **A list cell's content symbol is a live region reference, not a
  label.** `F1.ipl`'s list content (`B1`, `C1`, `A1`) works because those
  regions (`B0`, `C0`, `A0`) are pre-declared elsewhere in the same file.
  Inventing a symbol whose region was never declared produces
  `UNDEFINED REGIONAL SYMBOL` errors on load. Reuse an already-declared
  region for arbitrary list content unless you have a specific reason to
  declare a new one.
- **The CLI harness no longer throttles to real-1620 speed by default**
  (`tools/cli/run1620.mjs`, `--real-time` to opt back in). Every prior
  `simple*.ipl` timing figure logged as "~15-16s" is now ~3-4s; don't be
  surprised if an old log entry's stated timeout looks unnecessarily
  generous.
- **`F1.ipl`'s crash is now localized to the exact IPL statement**: the
  very first `J66` call (add symbol to an empty output list), which maps
  to the interpreter's `COLSYM`/`RESBLK` ("reserve block") machinery, and
  is confirmed to be the very first real list-space allocation attempt in
  the whole run (checked via `FNDBLK`/`RESBLK` call counts across a full
  trace). Not yet root-caused -- next step is inspecting what's actually
  in memory at the `TF` instruction's operands (`NMBR`/`LADR`) right
  before the crash, versus what the interpreter expects to find there
  (probably a missing record mark).
- **When building a column-exact `.ipl` file from a known-working
  template, verify with an explicit column/token-position check
  (`re.finditer(r'\S+', line)` + start offsets) rather than eyeballing
  it or doing blind text substitution on the original comment strings**
  -- a blind `.replace()` on a template's comment text can silently
  shift later columns if the replacement isn't the same length,
  producing hard-to-spot alignment bugs.
