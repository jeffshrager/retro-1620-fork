## Work Done

### 1. `simple9.ipl`: `GET SYMB` is a push onto the H0 pushdown list, not an overwrite

Pushed `L1`, `L2`, `L3`, `L4`, then `H0` itself via five `GET SYMB` (op
`10`) calls with no print in between, then a single `J151` (print list).
Punch output came back in exact LIFO order (`H`/`H` header, then `L4`,
`L3`, `L2`, `L1` — the reverse of push order). Confirms `GET SYMB` pushes
onto a pushdown list headed by H0, and `J151` walks that list head-to-tail
— not a same-register overwrite, which is how every earlier single-push
`simple*.ipl` test looked.

**Follow-up correction (Jeff's own catch):** "generally speaking, pushing
to lists works... unless the interpreter has specialized code for H0."
Traced the full run (`--trace`, ~93,900 lines) and grepped for the two
list-space-allocator entry points identified in the prior session's
`F1.ipl` investigation (`FNDBLK` at `08002`, `RESBLK` at `08248`).
`FNDBLK` ran exactly 32 times — all during interpreter bootstrap, none
triggered by this program — and `RESBLK` ran zero times. So `simple9.ipl`
does **not** demonstrate that dynamic list growth works in general; H0's
pushdown push bypasses the block allocator entirely (almost certainly
fixed/pre-reserved storage, consistent with H being a reserved region
letter). The actual dynamic-list-growth primitive (`J66`/`COLSYM`, the one
that crashes in `F1.ipl`) remains completely untested by this result.

### 2. `simple10.ipl`: minimal, committed reproduction of the `F1.ipl` crash

Jeff asked for "a shorter version of F1 that just gets to the failure" to
start a dedicated experiment thread on this bug (rather than continuing
to reuse the untracked `notes/F1.ipl`). Built by reusing `F1.ipl`'s `E1`
(executive) + `F1` (worker) routine bodies and all six region
declarations verbatim, but shrinking the input list `K1` from 6 elements
to 1 (`K2`, self-referencing the already-declared `K0` region).

Confirmed exact match to the original crash: same check-stop (`MAR Check:
fetch() invalid memory address=70603`), and the monitor trace's last
successful step before the crash is the same `J66` call
("ADD THE SYMBOL TO THE OUTPUT LIST", the first attempt to insert a
symbol into a freshly-created empty list). 28 lines vs. `F1.ipl`'s 48,
and now a permanent, tracked starting point for further experiments on
this specific bug.

Found and worked around a load-time gotcha along the way: dropping the
*unused* `A0`/`B0`/`C0`/`E0`/`F0` region declarations (keeping only `K0`,
the one actually referenced) produced `UNDEFINED REGIONAL SYMBOL` errors
on unrelated-looking labels. Restoring all six declarations fixed it with
no other change — not explained, logged as a separate open question.

### 3. Established a standard place for trace output: `traces/`

Jeff asked for CLI-harness trace/switch output to be written to files in

### 4. Major result: the Ackermann(m,n>0) bug is the same LINK-field bug, not a separate one

Jeff asked directly whether Ackermann's failure is a different problem
from the `F1.ipl`/`RESBLK` crash. Checked `Ackermann-TEST.ipl`'s own
`CONSTANT`/`VALUE` cards (`K1`, `M0`, `N0`) and found the exact same
left-justification error fixed in the `simple*.ipl` series this week:
the value digit sits at column 56, not 60. Ran it as-is and confirmed the
signature: `K1` reads as `10000`, and `N` gets decremented by ~10000 per
recursive call instead of by 1 — a direct match to the "K1 replaces N...
reads back as 10000" symptom from the original (pre-this-week)
investigation notes in `Mod-3-4/README.txt`.

**First attempt at a fix was itself buggy** (worth recording as a
mistake, not just the result): an automated column-rejustify script moved
*every* character at column 56 to column 60 indiscriminately, which also
mangled unrelated fields elsewhere in the file that use column 56 for a
different, already-correct convention (region-size fields, and — worse —
it truncated two `J8` branch-target labels down to just `J`). That
corrupted test run produced a *different* check-stop
(`address=48000`), which was incorrectly reported as evidence of a
"second, different bug" in Ackermann. It wasn't — it was a self-inflicted
corruption from the fix script, not a real interpreter behavior. Caught
by diffing the "fixed" file against the original and noticing several
unrelated lines had changed.

Redid the fix narrowly — moving *only* the three CONSTANT/VALUE cards'
value digits from column 56 to column 60, diff-verified to touch nothing
else — and reran:

- `Ackermann-TEST-Fixed.ipl` (m=1, n=1): halts cleanly, prints the
  correct result, **3**.
- `Ackermann-Fixed.ipl` (m=3, n=3, the original full test case): halts
  cleanly, prints the correct result, **61**.

This resolves the entire "Ackermann(m,n) fails for any n>0 / TRAPPED ON
H2" problem that has been open since Paul Kimpel's original investigation
— it was never a pushdown/list-space exhaustion bug in the interpreter
(H2/PSHDN/GET1/GET3 internals, as originally suspected); it was a
hand-transcription column error in `Ackermann.ipl`'s own source, the same
bug class independently found via the unrelated `simple*.ipl` series.
Updated `software/IPL-V/Mod-3-4/README.txt`'s "Status" section with a
dated "RESOLVED (2026-09-12)" note explaining this, cross-referencing
`../simple/log.md` and the prior seshsum, and clarifying that the
still-open `RESBLK`/`COLSYM` crash (`simple10.ipl`) is a *separate*,
unrelated, and still-unresolved bug.

## Architecture Notes / Gotchas for next time

- **The Ackermann(m,n>0) bug is fully resolved.** It was the LINK-field
  left-justification bug (see `20260911b_seshsum.md`), not a real
  interpreter defect. Use `Ackermann-Fixed.ipl` / `Ackermann-TEST-Fixed.ipl`
  going forward, not the originals, for any further Ackermann-related work.
- **The `F1.ipl`/`RESBLK` crash is a separate, still-open bug**, now with
  a permanent minimal repro at `software/IPL-V/simple/simple10.ipl`. Don't
  conflate the two — they looked similar at a glance (both involve list
  primitives and both were once suspected to be H2/pushdown exhaustion)
  but have completely different causes and completely different fixes.
- **`GET SYMB`'s H0 pushdown push does not exercise the same allocator as
  `J66`/`COLSYM`.** A test that only pushes onto H0 tells you nothing
  about whether the general list-growth path works.
- **When writing an automated fix that touches specific card columns,
  diff the result against the original and verify only the intended lines
  changed before trusting a test run against it.** A too-broad
  column-rewrite silently corrupted unrelated fields (region sizes,
  multi-character branch-target labels) in a first attempt at fixing
  Ackermann, and the resulting crash was mistakenly reported as a genuine
  second bug. Caught only by diffing before/after.
- **Trace output now goes to `traces/` at the repo root** (gitignored),
  named `<program>_monitor.log` / `<program>_instr.log`. Redirect output
  there directly rather than piping through `tail`/`grep` and discarding
  it, so traces stay inspectable after the fact.
