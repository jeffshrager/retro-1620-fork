### 2. A real, reproducible harness bug: found and fixed

Jeff's own `simple2.ipl` (meant to compute 3+4) hit "Multiple instances of
`this.run()` active" deterministically -- at the exact same point in
loading, every time, unlike the flaky version seen with Ackermann last
session. Root cause: `HeadlessTypewriter.control()`'s fire-and-forget
`.then()` callback (see `Processor.js`'s K/Control op dispatch) needs to
resolve no faster than the real device's slowest interlock
(`Typewriter.returnInterlock`/`indexInterlock` = 124ms) to avoid two such
chains overlapping. The previous 5ms delay (from last session) worked
most of the time but wasn't reliable. Bumped to 130ms in
`tools/cli/HeadlessTypewriter.mjs`; confirmed fixed.

### 3. Two straightforward bugs in `simple2.ipl`, found and fixed

- `N3`/`N4` were used as data-term names without ever being covered by any
  `DEFINE REGIONS` declaration (only region `A0` was declared) --
  "UNDEFINED REGIONAL SYMBOL" errors. Fixed by renaming into the
  already-declared `A` family (`A2`/`A3`, later `A3`/`A4`).
- The declared region size was one cell too small for the number of named
  cells actually used (`A0`..`A5` needs size >= 6). Jeff fixed this
  himself; bumped to 7 for headroom.
- **Jeff also caught his own transcription error independently**: the
  primitive he intended to call was `J110` (addition), not `J100` (which
  turned out to be a "GENERATOR" routine, unrelated to arithmetic --
  found by reading its actual assembly, under a `****** GENERATORS`
  section header in `IPL-V-Interpreter-Mod-3-4.sps`).

### 4. Isolated primitive tests (`simple3`/`simple4`/`simple5`) -- initially all "silently no-op"

- `simple3` (J110, 1 pushed operand): result unchanged (3, not 4).
- `simple4` (J111, 2 pushed operands): result unchanged (4, not -1 or 1).
- `simple5` (J125, 1 pushed operand): result unchanged (3, not 4).

Jeff pushed back hard on an early explanation attempt ("K1 has to exist
as a system-wide constant for GET3 to work" -- correctly called this "a
ridiculous hypothesis"). That forced actually reading the assembly instead
of pattern-matching: `GET3`/`DOIT` (`IPL-V-Interpreter-Mod-3-4.sps`) fetch
THREE stack items for J110/J111 -- a destination-name (preserved via `D4`
and restored after the fetch), then two real operands (`D5`, `D6`), with a
`BADIND` validity check on each. Give it fewer, it silently fails the
check and leaves H0 untouched. This is Newell et al.'s own documented
idiom (manual, S1 example, p.44 area): push the accumulator's name twice
(once as operand, once as destination).

Adding a real 3-operand setup (`simple8`: push A4, push A3, push A3
again, then J110) **produced a directly-traced, confirmed-correct add**:
the raw `A` (Add) instruction showed operands `30000`/`40000` (a
"value x 10000" encoding) combining to `70000` = 7. First primitive
confirmed correct under our own control, not just by matching a reference
trace.

### 5. J125 (increment) still doesn't fit the same picture

J125's actual `AM H0-5,1,610` modifies a *different* field than J110's
add -- the last few digits (matching the manual's stated "mantissa lives
in LINK", p.44, which Jeff pointed to directly) -- not the "x10000" field
J110 operates on. Traced Ackermann(1,0)'s own N0 directly: its LINK field
genuinely goes 0->1->2 across two real J125 calls, matching the expected
math exactly. But N0's *declared* value is also 0, so this can't
distinguish "J125 correctly reads N0's declared value" from "LINK always
starts at 0 regardless of any declared constant" -- a degenerate case.
Not yet resolved: what a `CONSTANT n` card actually needs to look like to
seed a non-zero starting value into LINK specifically (if that's even the
right question -- see next item).

### 6. Major methodological correction: `PRINT RESULT` output does not go where we thought

Traced `simple.ipl`'s raw typewriter buffer byte-for-byte:
`"\n   0 18935           THE END                     2"` -- no "3"
anywhere, despite `A1` being declared as `CONSTANT 3`. This is *not* a
regression -- Paul's own README already described `simple.ipl` as "runs,
but effectively does nothing," so nobody had ever verified it prints
anything. But it forced a bigger correction: J152's actual result output
goes to the **card punch** (via SYMOUT), not the typewriter -- confirmed
by re-running Ackermann(1,0) with **no switches at all** and finding a
clean `N  01  2` in the punch output regardless. The typewriter's
"THE END `<n>`" is a separate, generic completion message; its trailing
number does not reliably track the computed result (`simple7` showed `4`
matching 3+1, but `simple8` showed `6`, not the correct 7 -- likely
coincidence in the first case, not signal).

This reframes the *previous* session's "is Ackermann(1,0) really
validated?" question: N0's LINK-field increments are now directly,
mechanism-level confirmed correct (not just "matches a reference trace"),
independent of Program Switches.

### 7. Checked and ruled out: is this Paul's odd/even TNF bug recurring?

Jeff's hypothesis: could the J125-vs-J110 field discrepancy be a
recurrence of the TNF-odd-address issue Paul described (Modification

remain unchecked.

## Architecture Notes / Gotchas for next time

- **`J110`/`J111` need exactly 3 stack entries** (destination-name pushed
  twice + one real operand), per `GET3`/`DOIT` in
  `IPL-V-Interpreter-Mod-3-4.sps`. Confirmed working correctly when given
  this. This matches the manual's own documented idiom (p.44 area) --
  it's not a University-of-Oregon-specific quirk.
- **`J125` operates on a different field than `J110`/`J111`'s arithmetic**
  -- the raw word's LINK-area last digits, vs. a "value x 10000" style
  encoding for J110's operands. Not yet understood *why* these differ, or
  whether that's by design (two legitimate data-term conventions) or a
  real inconsistency. This is the most important open thread.
- **`PRINT RESULT` (J152) writes its actual result to the card punch via
  SYMOUT, not the typewriter.** Always check `cardPunch.cards`, not
  `typewriter.buffer`, when verifying a computed value from any future
  test file. The typewriter's "THE END `<n>`" message is a separate
  system-level completion notice; don't trust its trailing number as the
  result.
- **Don't trust a single matching data point as confirmation** -- this
  session had two false-positive moments (`simple7`'s "4" looked like
  confirmation of J125 until `simple8`'s "6" broke the pattern; an early
  "K1 must be a magic system constant" theory was built on too little
  evidence). Jeff's pushback each time ("ridiculous hypothesis", "did we
  validate F1?", "so now simple doesn't work?!") was the actual mechanism
  that kept this session honest -- lean into that scrutiny rather than
  resist it.
- **Next concrete step**: reconcile J125's LINK-field target with J110's
  "x10000"-field target -- ideally by finding a test case where a J125
  increment starts from a genuinely non-zero, verifiably-seeded LINK
  value (not the degenerate "declared 0, LINK also starts at 0" case that
  Ackermann's N0 represents), or by reading J125's SPS source
  side-by-side with GET1's shared `DOIT` logic as carefully as GET3 was
  read this session.
