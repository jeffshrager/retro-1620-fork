## Work Done

### 1. Built a headless CLI driver for the emulator

`emulator/Processor.js` and siblings have no DOM dependencies; only
`webUI/*.js` does. New: `tools/cli/run1620.mjs` +
`HeadlessCardReader.mjs`/`HeadlessTypewriter.mjs`/`HeadlessCardPunch.mjs`,
plus a root `package.json` (none existed). Full usage is now documented in
`tools/cli/README.md` (written this session). Headless devices reuse the
real `webUI/Typewriter.js`/`CardPunch.js` static translation tables
directly (confirmed safe to import — no DOM access at module load time)
rather than duplicating that data.

**Fixed along the way:**
- A genuine emulator bug: enabling `processor.tracing` before the very
  first LOAD/INSERT crashed, because `insert()` synthesizes the initial RN
  directly (bypassing normal instruction decode), leaving `opThisAtts`
  null when `enterICycle()`'s trace path dereferences it. Fixed in
  `emulator/Processor.js` (added a null check).
- The driver not exiting after timeout — `Processor.run()` re-invokes
  itself fire-and-forget from device callbacks and `envir.throttle()`
  keeps re-arming real timers, so the event loop never empties on its
  own. Added an explicit `process.exit()`.
- A "Multiple instances of `this.run()` active" check-stop, caused by the
  headless devices responding too synchronously/instantly compared to the
  real (always-at-least-slightly-async, physically-timed) browser
  devices. Fixed by adding real async yield points (a small `setTimeout`
  in `HeadlessTypewriter.control()`) and a "wait for the idle state to
  settle across several polls" delay before auto-pressing START.
- Added `--trace-after <cards>` / `--trace-delay <ms>` to `run1620.mjs`:
  a full `--trace` from cold boot is dominated by the load deck and,
  worse, by the interpreter's own post-load H2 free-list initialization
  (tens of millions of trace lines for a few seconds of real execution) —
  these let you skip straight to the program logic you actually care
  about.

**Validated:** the harness reproduces Paul's saved IPL-V-level traces
byte-for-byte for both Ackermann(1,0) (succeeds) and Ackermann(1,1)
(fails, matching his exact failure signature), and reproduces the
original (un-patched) decks' Punch Check garbage exactly. High confidence
the harness itself is correct.

### 3. Chased the Ackermann recursion bug via raw instruction tracing — partially retracted

Using `--trace-after`/`--trace-delay`, traced backward from the exact
monitor-trace step where region M0's value first goes wrong (address
19211, second visit, per the IPL-V-level switch trace). Found a specific
instruction pair (runtime addresses 07538/07562: a Subtract whose Q
operand reads as 10000, followed by a Transmit storing the result into
what was believed to be M0's address) that reproduces the corruption
pattern on every recursion level.

**This was subsequently called into serious doubt.** Attempting to test
the hypothesis directly — patching K1's word in memory to see if the
runaway stops — required first confirming the *runtime* address of K1
(the static SPS listing's address, 18647, was already known to be
unreliable for J-primitives due to load-time relocation; assumed but not
verified that data regions wouldn't have the same problem). Reading back
memory at the documented M0/K1 addresses, even well after execution had
demonstrably started (waited for "MONITOR POINT" text to appear), showed
all zeros — meaning region addresses are *also* subject to
relocation/indirection at runtime, not just the J-primitives. So the
07538/07562 finding, and the address-based reasoning behind it, should be
treated as unconfirmed, not as a located bug. The `Mod-3-4/README.txt`
Status section reflects the state as of the *previous* session's
conclusion (the instruction-pair finding); it has not yet been corrected
to reflect this session's retraction.

### 4. Stepped back: no verified model of IPL-V's execution semantics

Directly asked whether I actually understood how the Ackermann IPL-V
program works. Honest answer: the *algorithm* (standard Ackermann
recursion, matching the source comments), yes — the *execution model*

stack, how a regional symbol resolves to an address at runtime), no. That
gap directly caused both the trace-column misreading earlier and the
address-relocation confusion in Sec. 3. Agreed with Jeff to stop
inference-driven tracing on Ackermann and instead build verified

## Architecture Notes / Gotchas for next time

- **Address relocation is pervasive, not just for J-primitives.** Already
  knew static `.lst` addresses for J111/J117/J125/J152 don't match
  runtime (loader relocates them). This session found region/data
  addresses (M0, K1) are *also* unreliable at the addresses the listing
  documents — reading them back at runtime, well after execution started,
  showed all zeros. Don't trust any address from a static listing without
  independently confirming it against runtime behavior (e.g. the IPL-V
  switch-trace's own reported addresses, which *are* runtime-accurate).
- **Async timing matters in the headless devices.** The real browser
  devices are never perfectly synchronous (physical card/typing motion
  delays); the headless replacements need to preserve *some* asynchrony
  (a yield point) even where no real delay is being modeled, or
  `Processor`'s own fire-and-forget `run()` re-entry logic can race itself.
- **`--trace` alone is impractical from cold boot** — always combine with
  `--trace-after`/`--trace-delay`, and expect to need several real seconds
  of delay to get past the interpreter's H2-list-initialization phase, not
  just past card loading.
- **Next concrete step (per Jeff's direction):** don't return to
  Ackermann's raw traces yet. Get F1 loading and matching the manual's
  Fig. 2 trace first — that's a verified-correct, fully-documented ground
  truth to build real IPL-V execution-model understanding against, before
  trusting any interpretation of Ackermann's more complex trace. If F1
  keeps failing, suspect the transcription (E1's "13" op-code, the K1
  list-data cards) before suspecting the emulator or interpreter.
- `notes/` holds material Jeff has supplied across sessions (Paul's email
  and zip, the RAND IPL-V manual PDF, `F1.tsv`/`T123.tsv`, and now
