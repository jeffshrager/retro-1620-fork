## Work Done

### 1. `simple11.ipl`: `J62` alone -- eventually confirmed working, after two wrong theories

Jeff built his own `simple11.ipl` from scratch (a much simpler setup than
my earlier F1-derived version): a statically-built `L1->L2->L3->L4` list,
pushing `L1` then `L3` via `GET SYMB`, then calling bare `J62` to locate
`L3`. It failed with an `OP CODE` runtime error. I threw out two
confident, wrong explanations in a row before landing on the real one:

1. A stack-order/calling-convention mismatch -- wrong, Jeff called it out
   directly ("you're completely confused").
2. A "J60/J62/J64 load as a cluster" theory based on misreading a
   switches-trace section as a subroutine-loading table -- also wrong,
   and rejected outright ("J62 can be called anytime"). Confirmed wrong
   by directly reading `IPL-V-Subroutines.card`: it's a fixed 80-line
   deck loaded in full, unconditionally, every run.

**Actual cause:** a plain column-alignment error. Jeff's card had `J62`
starting at column 48 instead of column 50 -- correct only when a
2-digit numeric op-code prefix occupies columns 48-49 first (as in
`10L1`/`10L3`), not for a bare primitive name. Jeff fixed the column
himself; reran and confirmed clean (one card punched, `THE END 4`).
Logged both wrong theories explicitly in `simple/log.md`, not just the
right answer, per the "record mistakes, not just results" practice
established earlier this session.

**Process incident along the way:** I made a second mistake mid-thread --
built a `simple12.ipl` that substituted `J64` for `J66` using the exact
same surrounding setup that worked for `J66` (missing `J66`'s own extra
`PSHDN`/`CF`/`TF` setup before it jumps into `J64`). Jeff caught and
rejected it before it ran. I then also over-aggressively "helped" by
re-deriving a similar file, which led to a sharp exchange and a direct
request to leave his files alone and let him drive. Restored a

### 2. `simple12.ipl` (Jeff's): `J64` alone succeeds

Built on the fixed `simple11.ipl`: locate `L3` (`J62`), then call `J64`
directly to insert a new symbol `L7` right after it, then reprint the
whole list. **Result: clean halt, no crash.** Punched list came back as
`L1, L2, L3, L7, L4` -- `L7` correctly inserted in the right place. This
ruled out "`J64` itself is broken" as an explanation for the `F1.ipl`
crash.

### 3. `simple13.ipl` (Jeff's): `J66` crashes even when it should be a no-op

Called `J66` directly (the combined locate-or-insert dispatcher) against
the same populated list, searching for `L3` -- already present, so
expected to be a no-op. **Result: crashed with the identical signature as
`F1.ipl`/`simple10.ipl`** (`MAR Check: fetch() invalid memory
address=70603`). Compared the raw instruction trace against `simple10`'s
saved crash trace: identical final `CF`/`TF` instruction pair before the
check-stop, not just the same address. Since `J62` and `J64` both work
standalone, this pinned the bug down to `J66`'s own glue code --
specifically the setup right before its branch into `J64` -- and also
suggested `J66`'s own found/not-found check may not be working (it took
the "insert" path even though `L3` was already present).

### 4. Root cause found: a Modification Letter 3/4 regression, not an original-interpreter bug

Jeff added `notes/J66.png`, a photo of the *original* (pre-Mod-3-4) SPS
assembly listing for `JJ66`, asking to check for a transcription typo.
Comparing it against both listing files already in the repo:

- `software/IPL-V/IPL-V-Interpreter-Listing.lst` (original): matches the
  photo exactly -- `BTM PSHDN,H0` is followed directly by `TF H0-5,D6`,
  no instruction in between.
- `software/IPL-V/Mod-3-4/IPL-V-Interpreter-Mod-3-4-Listing.lst` (after
  Paul's patch): has a `CF D6-4` instruction inserted between them
  (opcode 33, operand address 07165) -- which matches our crash trace's
  final `CF 33 07165 00000` step *exactly*.

No transcription error relative to the photo -- the `.sps` source
correctly reflects what it assembles to. But this reveals that
**Modification Letter 3/4, as applied in this repo, added a new
instruction to `J66`'s glue code that doesn't exist in the original
interpreter at all**, and `Mod-3-4/README.txt` never mentions this (it
only documents the unrelated `TNF` odd-address Punch Check fix).

**Confirmed by direct test:** reran `simple13.ipl`, then `notes/F1.ipl`
itself, against the *original*, unpatched interpreter deck
(`IPL-V-Interpreter-Deck-1.card`/`-Deck-2.card`, no Mod-3-4). Both ran
clean, no crash. `F1.ipl`'s output list came back correctly deduplicated
(`B1`, `C1`, `A1` from an input of `[B1,C1,B1,A1,A1,B1]`) -- this is the
exact program whose crash has been under investigation since before this
session even started, now confirmed working end-to-end.

One loose end, not yet explained: both unpatched runs' list output
carries an unexplained `04` prefix on each printed symbol (`04B1`, `04L1`,
etc.) not seen in Mod-3-4-interpreter list prints. Doesn't block the
headline result but should be understood before calling the unpatched
interpreter fully clean.

## Architecture Notes / Gotchas for next time

- **The `RESBLK`/`MAR Check` crash that has been open since before this
  session started is resolved.** Root cause: Modification Letter 3/4
  (`software/IPL-V/Mod-3-4/`) inserted a `CF D6-4` instruction into `J66`'s
  glue code that does not exist in the original interpreter and is not
  documented in `Mod-3-4/README.txt`. Using the original, unpatched
  interpreter deck (`software/IPL-V/IPL-V-Interpreter-Deck-1.card`/
  `-Deck-2.card`) avoids the crash entirely; `F1.ipl` runs correctly
  end-to-end against it.
- **This creates a real tension with the Mod-3-4 patch's own purpose**:
  Modification Letter 3/4 fixes a genuine, separate bug (`TNF` odd-address
  Punch Check errors). The original (unpatched) interpreter still has
  *that* bug. Neither deck is unconditionally "the good one" right now --
  whoever picks this up next needs to either (a) find out whether `CF
  D6-4` is genuinely specified by the real historical Modification Letter
  3 document and something else about its application here is wrong, or
  (b) surgically drop just this one instruction from `Mod-3-4.sps` while
  keeping the rest of the patch, and confirm both the `TNF` fix and the
  `RESBLK` fix hold simultaneously.
- **A bare `Jnn` primitive call (no numeric op-code prefix) belongs
  starting at column 50, not 48** -- column 48 is only correct when a
  2-digit op-code prefix occupies 48-49 first. Cost real time this
  session via an `OP CODE` runtime error that looked like a
  loading/calling-convention bug at first glance.
- **Don't theorize about interpreter-internal mechanisms (loader
  behavior, calling conventions) from trace output alone when a more
  mundane explanation (a column error) fits the evidence at least as
  well.** Check the mundane explanation first. This was called out
  directly and sharply this session; both wrong theories were disproven
  in under a minute each once actually checked (reading
  `IPL-V-Subroutines.card`, re-checking the card's own columns).
- **The unpatched interpreter's `04`-prefixed list-print oddity is still
  unexplained** -- worth understanding before relying on the unpatched
  deck as a long-term fix rather than a diagnostic tool.
